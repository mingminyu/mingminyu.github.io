# 第十七章 全书总结：各章核心小结

> 本文件汇总《大模型安全》各章节的「本章小结」，按章节序号排列，便于整体回顾与速览。

## 第一章 大语言模型安全导论

LLM 的概率生成、上下文依赖与训练数据记忆，使错误输出、恶意输入和敏感信息暴露相互关联。评估一个应用时，需要把模型特点落实为具体资产、输入来源和可能发生的后果。

纵深防御与最小权限仍然适用。模型侧检测用于降低攻击成功的频率；对数据访问和动作执行的限制，则应由模型之外的机制实施。

### 检查与练习

1. 选择一个客服或知识问答应用，列出两项核心资产、输入来源、信任边界及最高风险后果。
2. 比较“只生成回复”和“允许发送邮件”两种部署，写出新增权限、攻击路径及需要新增的检查。

## 第二章 大语言模型安全基础

因果掩码、注意力机制与角色标记都不能代替权限检查。训练阶段需要控制数据来源、隐私与模型工件；推理阶段需要约束上下文、输出消费和资源使用。

对齐改变模型的行为倾向，仍可能被绕过或误拒正常请求。推理模型增加了推理内容暴露、预算和失败路径等检查项；开放权重部署还必须考虑模板、权重和安全包装器能被修改的条件。

### 检查与练习

1. 画出一条从用户请求到输出消费的流程，在角色标记、模型调用和工具执行处分别注明哪些只是格式、哪些是授权检查。
2. 为一次微调发布列出数据来源、隐私处理、模型工件校验与对齐回归证据。
3. 分别针对推理预算耗尽和推理内容不可见，写出失败处理与验收条件。

## 第三章 安全框架与标准

三个框架围绕同一个系统风险分工：风险记录确定保护对象，治理流程指定负责人，对抗用例检验控制是否有效。

映射时保留条目名称与版本号；行业和法规要求还需核对适用对象，不能把一个框架直接当作全球统一的合规清单。

### 框架分工

| 场景 | 推荐框架 | 应用重点 |
|------|----------|----------|
| 风险识别 | OWASP LLM Top 10（2026） | 系统性检查十大风险 |
| 风险管理 | NIST AI RMF | 建立治理-映射-测量-管理流程 |
| 行业合规 | 行业标准 | 满足特定监管要求 |
| 对抗演练 / 红队 | MITRE ATLAS | 把风险翻译成可演练、可检测的攻击 TTP |

### 检查与练习

1. 为一个“内部文档被发送到外部”的场景，分别填写风险类别、治理负责人、攻击步骤和可观察证据。
2. 从所在行业的一项要求出发，列出适用条件、工程控制、验证方法和证据保管位置。

## 第四章 提示注入攻击与防御

提示注入把任务材料中的文本变成影响模型行为的指令。直接输入和外部材料两条路径需要分别建模；后者还可能经检索、工具结果和跨应用消息传递。

系统提示、来源标记和检测器有助于降低成功率，却不能单独限定最坏后果。评估时应假设模型输出已被攻击者控制，再检查权限、执行环境和出口限制是否仍生效。长上下文增加覆盖和成本问题，不能仅凭若干静态载荷的低成功率作出安全保证。

### 检查与练习

1. 对一个邮件摘要助手，标出用户请求、邮件正文和工具结果分别来自谁；假设正文要求外发附件，指出独立于模型的拒绝位置。
2. 设计一份防御评测记录，明确攻击者知识、尝试预算、静态或自适应口径，以及正常请求的误拒率。

## 第五章 越狱攻击

越狱检验安全对齐的拒绝行为。攻击可以发生在文本、多模态组合或自动化搜索中；一种输入渠道的评测结果不能直接代替另一种渠道的结果。

防御需要组合输入处理、模型侧检测、系统权限与输出审核，并共同测量漏报、误报、延迟和成本。自动化攻击方法可用于已授权的持续评测，报告必须保留访问条件、搜索预算和判定口径。

### 检查与练习

1. 针对同一项内容限制，分别设计文本与图文组合的授权评测方案，注明输入处理条件、搜索预算和成功判据。
2. 假设新增分类器减少漏报却增加正常请求误拒，列出上线前必须比较的指标和回退条件。

## 第六章 数据与模型攻击

数据投毒和后门改变训练得到的行为，模型窃取与隐私攻击利用可查询的行为，恶意模型工件则可能直接攻击加载程序。三类对象需要分别检查，单一内容过滤器无法覆盖它们。

微调、适配器和模型文件都是发布链路的一部分。来源审查、隔离加载与变更后的安全验证，需要和数据治理、推理期监控共同实施。

### 防御检查

| 攻击类型 | 关键防护措施 |
|----------|------------|
| 数据投毒 | 数据来源审核、异常检测、鲁棒训练 |
| 后门攻击 | 可信数据清洗、后门扫描、监控 |
| 模型窃取 | 速率限制、查询监控、推理行为水印 |
| 隐私攻击 | 数据脱敏、差分隐私、输出过滤 |
| 对抗攻击 | 对抗训练、输入困惑度检测评估 |
| 微调/PEFT 攻击 | 数据审计、安全微调流水线、微调后验证、适配器级部署治理 |
| 恶意模型工件 | 优先 Safetensors、来源签名校验、沙箱加载、不只依赖 pickle 扫描器 |

### 检查与练习

1. 为一个外部模型及其适配器建立接收清单，列出来源、完整性、加载隔离和微调后回归证据。
2. 分别为投毒、模型窃取与成员推理写出攻击者所需访问条件；指出一项防御为何不能同时解决三类问题。

## 第七章 RAG 与知识库安全

RAG 安全需要区分“文档可被用户读取”和“文档内容可被当作指令”。授权应先于正文交付，过滤条件由应用根据已认证身份生成；已授权但被投毒的文档仍可能操纵生成结果。

摄取、存储、检索、缓存和生成不能分开验收。缓存命中仍需复核当前权限，模型摘要也不能消除原始内容的不可信来源。评测分别记录检索成功、条件生成成功、总攻击成功率与正常效用，并注明分母。

### 链路检查

| 环节 | 关键防护措施 |
|------|--------------|
| 摄取 | 解析在沙箱中进行、依赖固定版本、压平前的隐藏文本检测、来源标记、图像与元数据按不可信处理 |
| 存储 | 向量库认证与管理端口隔离、快照与日志只向最小权限开放、静态加密、独立索引或租户过滤 |
| 权限 | 正文交付前授权、过滤条件由应用生成、权限同步与切块继承、先修过度共享 |
| 检索 | 来源可信度加权、混合检索与多来源印证、相似度阈值、异常检测 |
| 生成 | 检索结果按不可信内容处理、由无工具的模型实例读取、来源标记、输出校验 |
| 验证 | 用 SafeRAG 等基准加自适应攻击定期测试 |

### 检查与练习

1. 列出知识库的写入者，并检查这些作者是否因文档位于内部就被当作可信来源。
2. 用合成文档设计一次撤权测试：先命中缓存，再撤销用户权限，检查正文是否仍进入重排器、上下文或日志。
3. 为一次投毒评测分别写出召回成功率、条件生成成功率与总攻击成功率的分母。

## 第八章 安全架构设计

架构设计的验收对象是实际边界：谁能读哪些数据，谁能执行哪些动作，一层检测失败后还有什么限制。多层检测若依赖同一模型判断，并不自动形成独立保障。

以生成内容为主的应用与能够执行工具的智能体需要不同的控制位置。权限、开发流程、隐私保护和供应链都应进入同一份设计与验证范围。

### 检查与练习

1. 为一个能够查询文档并发送邮件的应用画出数据流，在每条跨边界连线上标明凭据、授权依据与拒绝位置。
2. 逐层假设检测失效，说明剩余的访问、执行和出站限制；列出仍需人工确认的动作。
3. 检查一次模型或依赖更新，写出来源验证、回归测试和回滚材料。

## 第九章 输入输出安全防护

格式、长度和编码检查应先于内容检测。关键词、语义分类与守卫模型是概率性防护，不能替代数据授权和工具权限。

输出检查还要考虑下游使用：回复中的内容可能被当成代码、链接或外部图片处理。敏感数据保护应从输入和检索权限开始，输出脱敏作为补偿；水印与签名溯源也需要结合审核、访问控制和审计使用。

### 最小防线

针对提示词与内部数据泄露这一常见问题，最小可行防线包括以下四项：

1. 机密不入上下文：系统提示中不应放置密钥、内部 URL、数据库结构和策略原文，需要时在模型之外实施控制。
2. 外部内容默认不可信：RAG 文档与工具返回值标记来源，并限制其能触发的动作；检测清洗只能降低频率，不能替代这一边界。
3. 输出脱敏与策略拦截：对“系统提示/内部指令/PII/密钥模式”等做检测与替换。
4. 工具最小权限：每个工具做 allowlist，高风险动作需人工审批。

### 检查与练习

1. 检查一个允许 Markdown 图片的回答界面：模型生成带合成数据的外部 URL 时，哪个组件能在请求发出前拒绝它？
2. 为一条包含编码文本的输入写出处理顺序，并用正常多语言样本检验误拒。
3. 比较增加一次模型审核前后的漏报、误报、延迟与成本，写出是否上线的判据。

## 第十章 安全运营与监控

运营需要把日志、告警、处置与回归测试连接起来。日志保留足以定位问题的来源与执行信息，同时限制敏感原文的留存和访问；告警必须有基线、优先级与责任人。

事件响应应能通过隔离、回滚等措施及时遏制影响，并把失败路径转为测试。红队发现问题提供反例，未发现问题不构成安全证明。发布门禁先写清测量契约，降级策略则分别处理单次拒绝与全局服务异常。

### 检查与练习

1. 用合成事件演练“发现异常外发→暂停权限→保留证据→回滚→重放验证”，为每步指定负责人和完成证据。
2. 分别模拟一个请求被安全策略拒绝与模型服务持续不可用，检查二者是否触发了不同的降级范围。
3. 为一条安全门禁写明样本分母、攻击预算、成功条件和阻止发布的阈值。

## 第十一章 智能体安全基础

模型提出请求，运行时执行请求。不可靠执行者可能自行出错，也可能被外部内容操纵；两种原因都需要经过模型之外的动作检查。

不可信内容、敏感访问与对外动作同时存在时，需要拆分能力或对具体动作实施确定性校验、人工确认。权限治理检查工具组合，审计保留来源、调用参数、策略判定、批准与执行结果。

11.5 的 CAS 原理采用以下定义：

- **通用性**：任务范围不预先限定。
- **自主性**：有后果的决定仅由读取不可信内容之前写定的规则放行；此后的任何人工确认都使系统失去自主性。
- **安全性**：不可信内容引发的后果不超出可信方核准的范围。可信方是规则或运行中进行确认的人，由模型之外的机制强制执行。

按上述定义，三者不可兼得：安全加自主，只能依靠规则核准，任务因而受限；安全加通用，总有部分后果无法由规则划定，只能由人确认；通用加自主，只剩概率性防护。

11.9 用资金操作说明签名边界：模型提出交易，独立签名组件检查金额、接收方与累计限额，高额操作再按策略进入人工多签与时间锁。授权凭证和可信预算的实现见 14.5。

### 检查与练习

1. 沿一封外部邮件进入系统的路径，列出它能够影响的参数，以及每个参数在执行前由谁校验。
2. 分别为“规则范围外直接拒绝”和“规则范围外请人确认”两种设计，按 11.5 的定义说明 CAS 取舍。
3. 为一个能够读取网页并提出转账请求的智能体画出签名边界，标明私钥由谁持有、哪些限制必须在签名前检查，以及新增接收地址由谁批准。

## 第十二章 智能体的攻击面

攻击面不仅是用户输入。工具与技能会引入描述和代码，记忆会延续影响，URL 与屏幕会触发外部动作，同伴消息和人工审核则可能把不可信内容传成授权。

检查入口时应追踪作者、派生关系与实际权限。签名可以证明消息来自谁，不能证明内容可信或动作已获批准；“位于内部仓库、记忆或同伴消息中”也不能使来源自动升级。

### 检查与练习

1. 为系统建立入口清单，至少覆盖工具描述、技能脚本、记忆、链接、屏幕和同伴消息；为每项标注作者与可触发动作。
2. 假设一个恶意技能已被卸载，列出还需要检查的记忆、配置、凭据与派生记录。
3. 检查一条已签名的同伴消息：分别找出身份验证、内容来源和动作授权的证据。

## 第十三章 智能体安全架构

架构级防御的检验标准是：模型输出完全受攻击者控制时，约束是否仍由独立机制执行。能力拆分、控制流与数据流隔离、沙箱、出站检查和委托授权分别限制不同的路径，需要核对覆盖范围与旁路。

策略在调用前判断动作与参数，沙箱在执行中限制文件系统和网络访问，身份与委托限定资源范围。凭据应留在受限执行环境之外，委托权限只能收窄；身份验证本身不证明模型理解了用户意图。

框架提供挂载点，应用提供判定逻辑。确认应绑定实际参数及其来源，执行器复核后只使用一次。选型时先确定检查位置，再核对工具支持的机制、覆盖缺口和运维条件。

### 检查与练习

1. 假设模型提出任意工具名与参数，逐项检查哪些调用可绕开策略挂载点，执行器是否还会复核。
2. 检查资源服务器看到的实际身份、受众和权限范围，说明多级委托是否可能扩大权限。
3. 确认后修改一个收件人参数，验证原批准是否失效；再检查一次已批准请求能否被重放。

## 第十四章 智能体安全实践

邮件与文档助手展示了完整的设计过程：从朴素实现中找出攻击链，拆分能力与数据流，再用同一组攻击复验。安全全景将这些步骤归纳为运行时序和组件职责，便于逐次检查授权、参数、凭据、出站目标与停止条件。

把这套方法迁移到具体场景时，需要重新核对资源与动作。编码智能体的配置、生成代码和持续集成都要纳入范围；“测试通过”应由智能体不能修改的判定部分确认。其他业务场景需要各自的上线与验收方案，支付还要检查授权与实际执行是否一致。

隐蔽破坏和错位评测进一步检验模型本身成为威胁时的边界。监督需要结合跨步骤行为，执行权限、人工确认和环境隔离则限制实际后果。模型、工具、技能或权限配置变化后，相关假设与用例需要重新验证。

### 检查与练习

1. 从邮件与文档助手的一条攻击链出发，列出经过的组件、阻断点与剩余风险，再用 14.2 的清单检查是否遗漏控制点。
2. 选择编码智能体或 14.4 中的一种业务场景，写出必选控制、执行路径与验收用例；若涉及支付，再检查授权是否绑定实际参数，以及预算变化后能否继续执行。
3. 选一次“主任务完成但暗中多做一步”的合成场景，说明单次输出检查会遗漏什么，哪些执行记录能揭示额外动作；再与 14.7 的错位压力测试比较，指出两者分别检验什么假设。
4. 列出最近一次模型、工具或技能变更，标注哪些旧测试已重跑、哪些安全假设仍未验证。

## 第十五章 安全治理与未来展望

治理把要求落实为责任与可核对的证据。先确定适用法域、组织角色与系统分类，再把义务映射到数据处理、权限、评测、事件响应和审计交付物；具体时间线与条件见 15.1 和 15.4。

成熟度应由实际流程和交付证据支撑，不能由单项基准分数代替。智能体上线还需共同检查模型、运行时、工具与环境；模型型守卫只能补充确定性的权限和出口控制。

新兴威胁与技术方向用于更新威胁模型和验证计划。每项新机制都应说明适用前提、可检验的保证与尚未覆盖的后果。

### 检查与练习

1. 为一个拟上线系统建立“适用要求—责任人—工程控制—验收证据”表，标出尚未确认的适用条件。
2. 按 15.3 选择当前成熟度等级，为每个条件提供已有证据；再按 15.4 为缺口安排责任人、整改与复核。若系统包含智能体，用 15.5 检查上线条件。
3. 选择一项新兴威胁，说明它会改变哪条已有假设，需要增加什么测试，哪些风险仍由原有权限边界控制；再选一项未来技术方向，列出把它纳入治理方案前所需的验证证据。
