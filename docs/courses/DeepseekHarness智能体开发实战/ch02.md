# 第二章：LLM Wiki 从原始文档到可追溯知识层

## 1. LLM Wiki的产生背景与工作定义

前两场课程已经建立了 DeepSeek Harness Studio、Workspace、Session、Agent Preset、Skills 与 Plugin/MCP 的基础操作和对象区别。进入 LLM Wiki 后，“知识库” 在实际项目中经常指向完全不同的对象：一个集中存放文件的目录、一套带全文搜索的文档站、一条先检索再回答的 RAG 链路，或者由实体和关系组成的知识图谱。它们都能帮助用户使用知识，却分别解决保存、查询、关系表达等不同问题。LLM Wiki 关注的是另一个容易被忽略的环节：原始资料已经存在之后，怎样把散落在不同文档中的知识持续整理为可以反复读取、彼此连接并回查依据的主题知识层。

这里的 “LLM Wiki” 是本课采用的工作定义，不是已经形成统一规范的行业术语。判断一个系统是否符合这个定义，应当观察它怎样处理来源、页面、规则、链接、查询和维护，而不能只看产品名称、页面外观或是否带有聊天框。

### 1.1 从查询时组织到持久知识层

2020 年的检索增强生成(Retrieval-Augmented Generation，RAG) 原始论文把参数化生成模型与显式的非参数记忆结合起来：系统在回答知识密集型问题时检索外部内容，再利用命中的内容生成结果。论文中的具体实现使用 WikiPedia 稠密向量索引，但它承担的核心职责是查询时取证并辅助生成，不等于规定了 2026 年所有 RAG 系统都必须采用同一种向量索引。

RAG 解决了“回答之前到哪里找证据”的问题，却没有天然规定“多次查询之间怎样保存已经形成的主题理解”。如果一个团队的资料分散在产品说明、设计记录、运维手册和故障复盘中，同一个概念可能在四份文档里各出现一部分。每次提问都可以重新搜索这些文件，但跨来源得到的主题结论通常只停留在当次回答中；下一次遇到相近问题，系统还要重新定位、阅读和组合来源。

2026年4月4日，Andrej Karpathy 发布的 [`LLM Wiki`](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) idea file 把另一种做法描述为一个 pattern：在原始来源与用户之间维护一层持久、互链的 Wiki，使已经整理出的知识不必在每次查询时从头派生。该文件还区分了 raw sources(原始来源)、Wiki与schema(结构和工作流规则)，并以 ingest(纳入来源)、query(查询)、lint(检查)等操作说明来源进入、知识读取与持续维护的职责。原件同时强调它表达的是一种模式，而不是特定实现；向量检索、MCP、具体目录和输出形式均可按需要选择。

图中是 Andrej Karpathy 公开的 llm-wiki.md ideafile 原件，不是标准规范。原件写道："incrementally builds and maintains a persistent wiki"。这支持持久、互链和增量维护的模式；不能据此推出 LLM Wiki 已有统一标准，也不能把它与 LLM Council 联系起来。

2026年5月提交的论文 [Retrieval as Reasoning: Self-Evolving Agent-Native Retrieval via LLM-Wiki](https://arxiv.org/abs/2605.25480) 则给出了—个具体研究系统：文档被整理为带双向链接的结构化 Wiki 页面，智能体通过 `search`、`read`、`follow-link` 等接口执行多步检索。它说明持久化的主题知识组织可以服务智能体检索已经有明确的系统化研究实例，但不能据此认定该论文与前述 ideafile 属于同一实现或存在已证实的直接影响关系。


2026年论文 Retrieval as Reasoning: Self-Evolving Agent-Native Retrieval via LLM-Wiki 摘要将其研究对象表述为:"external knowledge as a compilable composable, and self-evolving sururture"。这支持持久化知识结构服务智能体检索已有特定论文实现；不能证明它与 Karpathy 的 ideafile 同也不能把论文中的 Error Book、双向链专或工具楼口规定力通用标准。

这条发展线并不是“文档搜索先被 RAG 淘汰，RAG 又被 LLM Wiki 淘太”的营代史。更准确的理解是：又档保存、查询时险家构化关系表达E持久王题重组逐步形成了可以组合的不同层一个完整系统完全可以同时保留原始文档、维护主题WikI、建立图结构，并债用RAG回答问题


### 1.2 本课采用的 LLM Wiki 工作定义

在本课中，LLM Wiki指：**由 LLM 或智能体按照明确规则，把只读来源重组为持久、可互链、可回溯并能继续维护的主题知识层；查询优先读取这层知识，并在需要核验时回查原始来源**。

这个定义包含五项承重特征:

1. **来源与派生知识分离**：原始资料保存作者的原始叙事和事实上下文，不能为了方便整理而被知识页面覆盖。Wiki 页面是从来源形成的派生产物，可以重建、修订和更新。
2. **知识按主题持久化**：页面围绕概念、系统、操作或策略等主题组织，而不是机械地对每篇文档各写一份摘要。同一页面可以综合多篇来源，同一来源也可以支持多个主题页面。
3. **结论可以回查依据**：来源引用回答“这条结论依据什么”。引用必须能回到真实原件；页面存在、文字流畅或模型自称已核验，都不能替代这一关系。
4. **页面之间存在可用连接**：内部链接回答 “理解当前主题后还应读什么”。链接用于扩展上下文和形成导航，但链接数量本身不代表知识质量，也不能自动把 Wiki 变成完整知识图谱。
5. **知识层具有维护机制**：新来源进入后，系统需要识别受影响页面，处理陈旧、冲突、缺链和孤立页面，并保留变化记录。所谓 “持久” 不是内容写入后永久正确，而是知识有明确位置，可以持续检查和修订。

这五项特征描述的是知识层的职责，不是固定技术栈。Markdown、特定页面元数据头、固定页面类型、机器清单、浏览器界面、向量数据库和知识图谱都可以成为某个实现的一部分，却不是所有 LLM Wiki 必须具备的统一组件。本课后续出现的目录名、页面数量和浏览方式，也只是为了把这些职责放进一个可观察的小型实例。

### 1.3 六类对象怎样组成知识链

LLM Wiki 的核心并不是一批页面，而是一条能够从结论返回依据、从当前主题继续扩展、从新来源触发维护的对象链。

```mermaid
flowchart LR
    A["原始资料"] -->|"按规则重组"| B["持久主题页面"]
    B -->|"导航与互链"| C["人或智能体读取"]
    C --> D["新来源、陈旧、冲突、缺链与孤立页面"]
    D --> E["维护检查"]
    B --> |"来源回查与核验"| A
```

这条链中的对象分别承担以下职责：

| 对象 | 主要职责 | 不能由什么信号替代 |
| --- | --- | --- |
| 原始资料 | 保存原始事实、上下文、版本和出处，是后续结论的事实入口 |文件已经被模型读过，不代表其中事实正确或已经形成知识层 | 
| 主题页面 | 把跨文档信息重组为可反复读取的概念、系统、操作或策略知识 |一文一摘要或把原文切成小文件，不等于完成主题重组 |
| 规则层 | 约束页面结构、引用方式、链接方式、证据不足处理和更新责任 | 有一份规则文件，不代表规则已经被执行 |
| 来源引用与内部互链 | 分别提供事实回查和上下文扩展 | 链接多、页面多或界面精美，不代表结论可靠 |
| 导航、维护记录与机器清单 | 让人找到页面，让维护者看见变化，让程序稳定读取当前知识对象 | 统计一致只能说明对象对得上，不能自动证明内容正确 |
| 查询与维护动作 | 一个最终答案或一次成功运行，不能证明查询过程有依据 | 定位页面、沿链接补充、必要时回查来源，并检查冲突、陈旧和孤立知识 |

例如，一个关于 DSH Agent Preset 的主题页，可以同时引用 Workspace、Preset、Skills、Plugin/MCP 和权限资料；它又可以链接到能力分层、团队委派和凭证边界等相关页面。来源引用保留事实依据，内部互链提供阅读路径，页面本身保存跨来源形成的主题理解。三者缺少任意一项，系统都会退化：没有来源，结论难以核验；没有主题重组，只剩文件索引；没有维护，持久页面会逐渐变成过期副本。

对象地图在这里暂时只说明“持久主题重组”要承担什么职责：主题对象应当脱离单篇文档的章节顺序，同时保留来源关系和后续维护入口。原文片段究竟怎样进入第一个页面，跨来源内容又怎样形成一个共同主题，仍需要到真实文件中逐项回答，不能由这张对象地图预先给出完成结论。

### 1.4 文档库、RAG与知识图谱的位置

文档库、LLM Wiki、RAG 和知识图谱不是四个只能选择其一的产品类别，而是可以叠加的职责层。

- **文档库提供原料**：核心产物是原始文件及其目录、元数据和版本。它擅长保存原件，也可以提供全文搜索；但“能够搜索文件”不代表跨来源主题知识已经形成。
- **LLM Wiki组织持久知识**：核心产物是主题页、来源引用、内部互链和维护记录。它把资料进入后的持久主题重组放在查询复用之前，减少相近问题反复从原始叙事中重新组织主题的需要。
- **RAG提供查询机制**：核心动作是先检索证据，再用证据增强生成。检索对象既可以是原始文档，也可以是Wiki页面或其他索引；是否使用LLMWiki，不由“有没有聊天框”决定。
- **知识图谱提供显式关系表示**：核心产物是带明确语义的节点、边及其派生结构。Wiki 页面和内部链接可以投影成图，但普通页面链接并不自动具备实体类型、关系语义、消歧和图查询合同。

图中是 2020年原始 [RAG 论文](https://arxiv.org/abs/2005.11401)的 arXiv 标题与摘要页。摘要把论文方法表述为：“combine pre-trained parametric and non-parametric memory for language generation"，这支持把 RAG 定位为检索增强生成机制；论文实例使用 WikiPedia 稠密向量索引，但不能推出所有 RAG 都必须使用同一种向量库。

[Microsoft GraphRAG](https://microsoft.github.io/graphrag) 是这种可组合关系的具体例子。其官方流程会从 raw text 形成实体、关系、社区和社区报告，再以Local、Global、DRIFT 等方式查询；Local Search 还可以同时使用图数据与原始文本片段。GraphRAG 因而是一种利用图结构增强检索与生成的具体系统，不是所有知识图谱的同义词，也不是 LLM Wiki 的替代名称。

图中是 Microsoft GraphRAG 官方文档主页内容，画面直接显示知识图谱和过程说明。官方将 GraphRAG 称为：“structured,hierarchical approach to Retrieval Augmented Generation (RAG)"，这支持 GraphRAG 从原始文本抽取图、构建社区层级与摘要，再把这些结构用于RAG；不能把Markdown 互链直接等同知识图谱，也不能把 GraphRAG 当作所有知识图谱的定义。

面对一个新系统时，可以用三个问题先确定各对象的位置：**事实原件保存在哪里；跨来源主题知识是否在查询之外被持续保存；一次回答怎样找到证据并回到原件**。如果系统还显式维护实体与关系，再继续检查图结构由什么抽取、怎样更新、支持什么查询。这样的判断不依赖产品命名，也不会把浏览界面、检索算法和知识组织层混为一谈。

### 1.5 价值、适用条件与停止边界

LLM Wiki 的主要价值来自知识的持续复用，而不是页面形式本身。

- **减少重复理解**：稳定的主题页让后续查询先读取已经形成的知识，再按需要回查来源，而不必每次从多篇作者叙事重新开始。
- **支持跨来源重组**：产品规则、实现说明、故障记录和安全边界可以围绕同一主题汇合，同时保留各自依据。
- **兼顾人和智能体阅读**：人可以沿导航和链接建立系统认识，智能体可以读取结构化页面、来源和机器入口继续执行任务。
- **保留可追溯性**：结论可以回到原始资料，新增证据也能定位受影响页面，使知识更新具有可检查对象。
- **形成渐进维护入口**：冲突、陈旧、缺链和孤立页面可以被持续发现，而不是散落在一次性回答中。

这些价值成立需要相应条件。语料通常包含多份有交叉关系的资料；同一批知识会被团队反复查询、解释或用于后续任务；来源能够保留版本并允许引用；主题结构具有一定稳定性；同时还需要明确的规则和维护责任。团队知识、长期项目文档、持续研究资料、客服知识和运维经验通常具备这些特征。

如果任务只是查询单篇短文中的一个事实，或者资料只使用一次，额外维护主题层的成本可能高于收益。资料变化极快却没有维护责任、来源无法保存版本、权限不允许建立派生知识，或者系统只需要确定性字段查询时，也不应因为名称新颖而强行引入 LLM Wiki。

LLMWiki还不能自动解决来源错误、事实冲突、知识过期、权限治理和回答幻觉。它不会因为使用LLM就自然获得正确性，也不会因为具有互链就自动成为知识图谱，更不会因为可被查询就自动具备高质量RAG。大规模切分、Embedding、向量数据库、召回与重排、实体抽取、社区聚类、自动冲突消解、多租户、审计、容灾和评估，均属于需要单独设计和验证的工程能力。


因此，判断 LLM Wiki 是否成立，最小标准不是 “生成了多少页”，而是 **原件是否保留，主题知识是否持久，结论能否回查，页面能否扩展，新增证据是否有维护入口**。下一步将把这套关系放进四篇内容交叉的 DSH 原始资料中：先保留只有原始资料时的查询基线，再观察主题页面怎样在不改写原件的前提下形成。到那时，工作定义才会从对象地图进入真实文件。

## 2. 从原始资料到主题知识页

前一部分已经把原始资料、持久知识页、来源引用和内部互链放到了各自的位置。现在需要观察这组对象怎样在真实资料中形成。起点不是空目录，而是 `content/raw/` 中四篇已经可以搜索、也足以支持临时问答的DSH技术资料。问题恰恰在这里：**能搜索到原文，不等于已经形成可以反复读取的主题知识层**。

### 2.1 四篇 raw 保存的是来源原件

隔离 Workspace 的 `content/raw/` 中有四篇 Markdown:

| 来源 | 原文的主要叙事 | 与其他来源交叉的主题 |
| --- | --- | --- |
| `R1-dsh-workspace-session.md` | Workspace、Session `cwd`、持久历史与文件可见范围 | Preset 在 Session 中生效、权限边界、交付证据 |
| `R2-dsh-agent-preset.md` | Agent Preset 的 composition、生效时机与失败恢复 | Skill、Plugin/MCP、Subagent、Host 权限 |
| `R3-dsh-skills-plugins-mcp.md` | Skill、Plugin 与 MCP 的职责和各自成功信号 | Preset 装配、凭证、工具验收 |
| `R4-dsh-team-security-credentials.md` | 父子 Agent 委派、Session 权限与凭证消费 | Preset、Plugin/MCP、Workspace 可见范围、交付验收 |

这四篇资料都有完整标题、事实时间、运行版本和结论边界。例如 R1 解释Workspace 是对既有目录的持久登记，而 Session 是带 `cwd`、装配、权限和事件历史的运行对象；R2 解释 Preset 怎样组合角色、规则、Skill 与工具；R3 区分方法层、运行时装配和外部工具连接；R4 把委派、权限和凭证放在同一套有效边界中。它们不是为了 Wiki 临时拼出的短句，而是可以独立阅读的来源原件。

### 2.3 规则层约束派生知识怎样成立

原件与主题页之间还需要一层公开规则。隔离 Workspac e中的 `rules/wiki-contract.md` 不是第五篇业务资料，它不提供新的 DSH 产品事实，而是约束知识怎样形成、怎样回查以及证据不足时怎样停止。

规则首先分开两个目录：`content/raw/` 保存只读来源，`content/wiki/pages/` 保存可重建、可修订的主题页。随后定义四种页面类型：

- `concept`：解释一个概念及其边界；
- `system`：解释多个对象怎样组合并产生行为;
- `playbook`：给出可以迁移到相似任务的操作与判断顺序；
- `policy`：定义权限、安全、拒答或治理边界。

每页都使用同一份 YAML frontmatter，至少包含 `id`、`title`、`type`、`topic`、`slug`、`sources`、`links` 和 `updated`。正文再按“摘要一结论一来源证据一相关页面”的顺序展开。其中有两组字段最容易混淆：


| 对象 | 回答的问题 | 使用规则 |
| :--- | :--- | :--- |
| `sources` 与“来源证据” | 这条结论依据哪篇原件？ | 使用真实 raw 相对路径，并说明哪篇来源支持哪项结论 |
| `links` 与“相关页面” | 理解当前主题后还应读取哪个主题？ | 使用能够落到真实页面的页面 id，并在正文给出可打开的相对链接 |

因此，来源引用负责**溯源**，内部链接负责**扩展知识上下文**。一个链接即使能打开，也不能代替事实依据；一条来源引用即使准确，也不会自动告诉读者下一步该读什么。综合性建议如果不是原文直接陈述，还必须明确标为“本Wiki的操作性归纳”，不能伪装成来源事实。

规则文件只声明约束，不会自动产生合格页面。真正的判断仍要落到页面：字段是否齐全、来源是否真实、结论能否回到原文、相关页面是否存在，以及证据缺失时是否停止扩写。

单来源页和跨来源页把选择与重组过程展开之后，其余页面不再依赖一段不可见的DSH实时生成过程。八页终态由公开的 `page-specs` 与确定性的 `compile_wiki.py` 形成：页面内容先在公开规格中确定，脚本只按规格落盘并检查统一结构。它是透明复现工具，不是一个在课堂 Session 中自行理解四篇资料、即时创作八页的 DSH Agent。

初始页面集合覆盖四种页面类型:


| id | 页面 | 类型 | 主要问题 |
| :--- | :--- | :--- | :--- |
| P1 | Workspace、Session 与上下文边界 | concept | 目录登记、运行历史和文件可见范围怎样区分 |
| P2 | Agent Preset 的组合与生效 | system | 主 Agent 工作方式怎样装配并在新 Session 生效 |
| P3 | Skill: 按需加载的方法层 | concept | 文件存在、目录摘要、完整加载与任务结果怎样分层 |
| P4 | Plugin、MCP 与工具成功信号 | system | 发现、安装、挂载、调用和外部结果怎样区分 |
| P5 | DSH 能力层: 方法、工具、装配与委派 | concept | Skill、Plugin/MCP、Preset 与委派分别处于哪一层 |
| P6 | 父子 Agent 委派与回收流程 | playbook | 怎样定义写域、核验子产物并由父级汇总 |

![initial·P1-P8八页真实文档总览](images/35.png)

八个 initial 冻结Markdown的确定性排版总览，不是重新手写的知识卡片，也不是原生 WikiUI。八个格子均保留各自的 `id`、标题、类型、主题、来源、链接、更新时间与正文开头，用于一次确认P1-P8真实存在。总览只能证明八页文件及其结构可见，不能用页面或链接数量证明知识质量，也不能把它们写成DSH实时生成结果。逐页原件：P1、P2、P3、P4、P5、P6、P7、P8。

读取任意一页时，都可以用同一顺序判断它是否成立：先看frontmatter中的页面身份、类型、来源和链接；再读摘要确认页面只回答一个稳定主题；然后逐项核对结论与“来源证据”;最后打开“相关页面”，确认链接指向的是另一个真实主题页。编译脚本如果遇到缺失字段、不存在的来源或无法落到真实页面的链接，应回到公开规格修正派生产物，而不是改写raw来迁就页面。

八页成立时，知识编译已经满足两个结构性条件：至少一个页面综合多篇来源，并且至少一篇来源支持多个页面。四篇raw仍保留作者叙事和只读身份，八页则提供按主题组织、可以修订和重建的知识层。这一结果只能说明当前缩微Wiki的页面结构、来源关系和互链成立；页面多、链接多本身不能证明结论质量，也不能把本课采用的八页与四种类型提升为行业标准。

到这里得到的仍是一组Markdown页面。知识编译已经完成，但页面集合还没有成为可持续读取的整体。

## 3. 导航、清单与可见查询

八个主题页已经按照同一规则形成，每页都有来源证据和相关页面。然而，页面存在并不等于知识层已经便于持续使用。缺少整体入口时，读者只能逐个翻找文件；缺少变化记录时，维护者无法判断这一批页面何时、由哪些来源形成；缺少结构化清单时，程序又只能临时扫描目录、猜测字段和关系。

![initial·机器清单manifest.json](images/38.png)

这是一张对修复后冻结 `manifest.json` 原件的确定性排版图。图中可见 `state: initial`、`page_count: 8`、`source_count: 4`，以及 P1 的 `sources`、`links`、`updated` 和 `sha256`；可在冻结的 `manifest.json` 原件中核对完整结构。尤其要观察这里的来源从清单所在目录出发写成 `../raw/`；页面 frontmatter 位于更深一层，才写 `../../raw/`。这张机器清单不能替代页面正文，也不代表查询保存态内嵌的、修复前清单与浏览验收清单字节一致。

`statistics` 提供这个冻结集合的总体规模；`pages` 则逐页登记稳定标识、自然路径、类型、主题、来源、内链和更新时间。程序由此不必解析索引中的自然语言，就能找到 P1、列出它的来源，或继续访问 P2 和 P7。完整清单还保存页面与来源的内容摘要值，用于判断对象在两次生成之间是否改变。摘要值只能回答“内容是否相同”，不能证明结论一定正确。

来源路径必须按“路径写在哪个文件里”解释。`manifest.json` 位于 `content/wiki/`，所以它回到 `content/raw/` 使用 `../raw/`；P1 页面位于 `content/wiki/pages/`，页面 frontmatter 回到同一 raw 则使用 `../../raw/`。两种写法的基准目录不同，不能为了表面一致而写成同一个字符串。查询保存态内嵌清单中的 `../../raw/` 是规范化修复前的历史记录，仍可证明当次查询看到了哪些字段，但不能作为修复后浏览来源链接的路径。

在修复后冻结态中，三个入口可以用 P1 交叉核对：`index.md` 把它列为概念页；`manifest.json` 把它登记为 `type: concept`，路径为 `pages/workspace-session-context.md`；打开页面后，frontmatter 中的 `id`、`type` 和 `links` 应与清单表达同一对象，分别按各自目录解析的 `sources` 最终都应回到 R1、R2、R4 原件。任何一层只有名称、没有真实目标，都属于断链。

这份 `manifest.json` 是 Wiki 自己的知识清单，不是课程制作或实验运行记录。初始状态下，四项统计应为 **8** 页、**4** 个来源、**4** 种类型和 **30** 条页面链接。统计相符说明对象关系可以被稳定读取，仍不能用页面数或链接数代替知识质量判断。

当前浏览入口只承担只读阅读。“LLM Wiki构建图谱”演示页尚不是可用入口，不能用尚未存在的页面替代这里已经可核查的薄浏览页。这个只读页也没有证明完整Web后端、问答服务、知识图谱或工业级权限系统已经存在。

### 3.3 真实查询回放的阅读方法

下面三次查询均来自官方DSHCLI 0.1.0-rc.7 的隔离 Session。每组材料保留两类原件：`raw-answer.txt` 是模型原始回答，`visible-trace.json` 是同次Session导出的脱敏可见事件。后者只包含用户消息、可见工具调用、工具结果和最终回答；系统提示、增量片段、凭证以及隐藏推理均未进入教材。

## 一、总览：四类对象各负责什么

`content/wiki/pages/dsh-capability-layers.md` (P5) 给出分层口径：

> **Skill 提供方法，Plugin/MCP 提供工具或服务连接，Preset 组合主 Agent 工作方式，Subagent/Workflow 在运行时执行委派。分层的目的，是为每个对象选择正确完成信号。**

四类对象可以协作（例如一个知识库 Preset 可以同时加载 Skill、装配 Plugin、经 MCP client 连外部服务），但文件格式、生命周期和验证入口都不同（P5 结论；`content/raw/R3-dsh-skills-plugins-mcp.md` 第 16-18 行）。

### 1. Skill — 按需加载的“方法层” (`content/wiki/pages/skill-method-layer.md` P3)

- **负责什么**：保存方法、步骤、约束与资源路由，回答“怎样做”。它只是方法文本，**不能凭方法文本本身创造外部工具能力**（P3 结论）。

### 2. Plugin / MCP — "可执行能力"层 (`content/wiki/pages/plugin-mcp-tools.md` P4)

| **完整 AI 应用** | 另一个产品层：拥有**专属 UI、专属数据与端到端流程**。完整应用可以在内部使用 Plugin 或 Preset，但不能因此被缩写成“一个插件”或“一份 Preset” | `content/wiki/pages/dsh-capability-layers.md` 结论与来源证据；raw 佐证：`content/raw/R5-dsh-studio-rc11-application-update.md` |

**关键边界**（`content/wiki/pages/dsh-capability-layers.md` 结论）：
- 四类对象（Skill/Plugin/Preset/Subagent+应用）文件格式、生命周期与验证入口不同，可协作但不能同义。

- 能力存在于源码/配置只说明"候选"，必须继续验证 Session 可见性、真实调用与直接结果（P5 结论）。

### 4.4 增量知识层的价值与维护责任

这次更新体现的价值不是“自动读到最新版”，而是变化可以被定位、复用和回查。R5作为原件独立保存，旧资料仍可读取；三个受影响页面把新事实放回既有主题；`log.md` 记录变化过程；`manifest.json` 为程序提供当前清单；固定问题再从索引、页面回到新来源。人和Agent因而读取的是同一组持久对象，而不必在每次提问时重新决定所有资料应怎样组织。

这种方式适合团队技术资料、项目规范、研究资料、客服知识和运维手册等场景：来源会逐步增加，同一主题散布在多篇文档中，结论需要被多次读取，并且回答必须能够回到依据。它尤其适合需要同时保留“原文由谁提供”和“跨来源主题怎样归纳”的知识工作。

它并不普遍优于简单文档管理。资料很少、只查一个来源中的单一事实时，直接浏览或全文搜索可能更合适；信息变化极快却没有维护流程时，持久页面反而可能迅速陈旧；来源错误、规则错误或归纳错误还会传播到多个页面和后续回答。互链数量、页面数量和一次问答成功都不是知识质量本身。

当前小型Wiki只证明了受控条件下的透明增量：新增一篇已知来源，更新三页，保持五页不变，再复查一个固定问题。它没有证明自动发现新资料、自动解决来源冲突、长期无人维护或任意规模下稳定更新。当新旧来源互相矛盾时，仍需要明确保留哪些表述、怎样标记时效、由谁裁决；当页面数量增长时，还需要处理陈旧页面、孤立页面、断链、重复主题和错误传播。

小型Wiki也不能继承同名完整应用的能力。当前对象只有Markdown主题页、来源引用、内部互链、`index.md`、`log.md`、`manifest.json`、薄只读浏览和文件级查询；它没有知识图谱、SQLite、生成式RAG、质量评估、多租户、完整权限审计或容灾能力。R5列出的文档、Wiki、知识图谱、溯源问答和质量评估属于完整FF-LLM Wiki的官方能力声明，不属于这个缩微实例，更不是已经在本机逐项验收的结果。

### 4.5 文档库、LLMWiki、RAG与知识图谱的统一辨析

四类技术不是按“初级到高级”排列的竞品，而是在同一知识系统中承担不同职责。使用统一维度比较，才能避免把文件、知识页、查询机制和关系结构混成一个“知识库”标签。

| 比较维度 | 普通文档库 | LLM Wiki | RAG | 知识图谱 |
| :--- | :--- | :--- | :--- | :--- |
| 核心产物 | 原始文件、目录和元数据 | 持久主题页、来源引用、内部互链与维护记录 | 检索索引、命中证据和基于证据的生成结果 | 带语义的节点、边与属性 |
| 组织时机 | 作者写作或资料收集时 | 来源进入后、查询复用前持续编译与修订 | 索引阶段准备检索对象，每次查询时取证并辅助生成 | 抽取、消歧、建图和索引阶段形成结构化关系 |
| 查询方式 | 目录浏览、关键词或全文搜索 | 从索引或搜索进入主题页，沿内链扩展，必要时回查来源 | 先检索相关证据，再把证据用于生成；可读取 raw，也可读取 Wiki | 图遍历、实体查询或路径查询 |
| 关系表达 | 主要保留文档作者原有目录和链接，跨文档关系可有可无 | 以主题页互链表达阅读与概念关联，可进一步投影成图 | 不强制显式关系；关系能力取决于所用索引和检索方案 | 以有语义的节点和边显式表达实体及其关系 |
| 维护责任 | 保持原件完整、版本清楚、权限合适 | 维护规则、来源溯源、冲突、陈旧、孤页、断链和增量更新 | 维护召回质量、证据约束、生成边界、拒答与降级 | 维护实体/关系质量、消歧、图更新、索引和查询策略 |
| 适用场景 | 保存原件、审阅正式文档、简单事实查找 | 跨来源主题重组、团队知识复用、人机共读和持续维护 | 面向问题的证据检索与生成式回答 | 关系密集、多跳关联、路径分析和全局结构问题 |

这张表得到的是组合关系，而不是替代结论。文档库提供可追溯原料，LLM Wiki把分散内容编译成持久主题知识，RAG在查询时检索证据并辅助生成，知识图谱显式表示实体与关系。一个完整系统可以同时拥有四层：原始文档进入知识编译，主题页和来源再形成检索索引或图结构，查询层按问题选择全文、向量或图检索，并把可核查证据交给生成模型。

以MicrosoftGraphRAG为例，它的索引流程还会形成claims、社区与社区报告，查询引擎提供使用社区报告的社区级检索。这些是GraphRAG这一具体系统的派生产物和查询机制，不是所有知识图谱都必须具备的通用组成。

边界同样需要明确。RAG不必使用某一种向量数据库，也不要求输入一定是原始文档；它可以检索Wiki页面。Wiki页面之间有链接，不等于已经具备语义知识图谱，因为节点类型、边语义和图查询合同仍需另行定义。GraphRAG是把图结构用于检索增强生成的一种具体系统，不是所有知识图谱的同义词。LLMWiki也不取代文档库：如果失去只读原件，主题页就失去了可回查的事实基础。

接下来真正需要回答的问题是：怎样自动处理更多来源，怎样让同一输入稳定重建相同知识产物，怎样加入完整检索与证据约束，怎样用固定评估发现退化，以及怎样把源码、数据、测试和使用说明组织成可接手的交付物。
