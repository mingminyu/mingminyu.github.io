# 第三章 认识最终项目：开发全路线与DSH环境装配

## 1. 最终产品与对象关系

上一模块（01）已经建立了从原始资料到知识页、索引、引用、互链和查询结果的基本对象关系。FF-LLM Wiki 把这条关系落实成一套完整产品：资料先进入可管理的处理流程，随后形成可浏览的 Wiki；知识页继续提供关系数据和检索证据；问答把证据送到用户面前；评估再检查整条链路是否稳定。完整产品的重点不在“页面很多”，而在同一批知识对象能够被连续生产、使用和检查。

### 1.1 两套成片呈现同一个产品目标

电影级演示负责建立整体目标。播放时先辨认 DSH 中的应用入口，再观察资料中心、Wiki、知识图谱、问答和评估是否始终属于同一套界面与数据语境。片中的开发画面是来自真实操作记录的蒙太奇，不能据此推断每一步的实现机制。

功能演示适合暂停观察状态变化：资料提交后经历处理过程，知识图谱读取已经形成的关系，模型先完成可用性验证，问答随后以流式方式返回正文与引用证据。视频保留了提交、处理中、完成和最终结果，因而可以确认这些状态确实出现在同一产品链中；它仍不能替代后续的源码和机制讲解。

### 1.2 七个入口组成一条用户旅程
#### 1.2.1 知识工作台：读取全局状态

知识工作台是进入系统后的总览。它同时读取知识资产统计、问答评估结果、构建流水线状态、最近资料和图谱预览，把分散在各页的结果汇总成一张运行地图。图中的47个知识页、98个来源引用、99条语义互链以及93.4的当前评估结果，都是这个版本的快照；工作台展示已有对象的状态，不负责替代各对象的生成过程。

![知识工作台](images/01.png)

#### 1.2.2 资料中心：让输入可管理、让失败可恢复

资料中心接收的是资料记录及其处理状态。默认列表把搜索、筛选、分页、类型、业务主题和处理状态放在同一入口；切换到“异常”后，可以看到失败原因和“重新处理”动作。提交重处理后，异常数由8变为7，处理中由10变为11，并出现明确反馈。这组前后状态比一张“完成”画面更重要：成功判断不是按钮被点击，而是目标资料离开原失败集合并进入新的处理状态。

#### 1.2.7 系统设置：管理问答运行条件

系统设置页消费模型服务状态、当前模型、知识数据状态和生成参数。初始画面显示凭证的脱敏状态；执行最小连接验证后，页面给出明确成功反馈。判断成功要看真实调用返回，而不是仅凭输入框里存在掩码。延迟数值是录制时的单次结果，不是其他机器上的性能承诺。

至此，七个入口可以还原为一条对象流：资料记录与处理状态进入知识编译，形成Wiki页面、引用和互链；知识层继续形成图谱合同与检索对象；检索证据进入回答，固定题库和运行报告再评估问答链。工作台读取全局结果，系统设置提供问答运行条件。任意一页脱离这条对象流，都只能说明局部界面存在，不能说明完整知识工程已经成立。

### 1.3 产品本体、DSHHost与最终应用插件

FF-LLM Wiki 可以从 DSH 启动，但产品并不“只存在于DSH页面里”。安装 `@fufan/dsh-plugin-11m-wiki@1.1.2` 后，DSH 应用中心出现 FF - LLM Wiki卡片和侧栏入口；点击“打开应用”后，DSH Host保持原页面，系统浏览器打开独立的完整知识工作台。

![](images/69.png)
![](images/01.png)

三个对象的责任边界如下：

| 对象 | 负责什么 | 不负责什么 |
| :--- | :--- | :--- |
| 完整 FF-LLM Wiki 项目本体 | 页面、API、SQLite 数据、资料处理、Wiki、图谱、问答与评估 | 不负责把自己注册到 DSH 应用中心 |
| DSH Host | 提供插件安装与启动环境、应用中心入口和平台凭证服务 | 不承载 FF-LLM Wiki 的七个产品页面与业务实现 |
| `@fufan/dsh-plugin-llm-wiki@1.1.2` | 封装同步的应用基线，增加 Host 启动、平台凭证传递和运行路径适配 | 不是产品本体，不是 Agent Preset，也不是开发期工具插件 |

![](images/70.png)

凭证关系也遵循这层分工。DSH模型设置只显示DeepSeek已配置状态，不显示密钥明文；最终应用插件通过Host的凭证服务把所需值注入服务端进程；FF-LLM Wiki设置页只显示脱敏状态，并执行最小模型验证。验收记录中的真实调用成功说明这条适配链当时可用，但不会把凭证写入前端、安装包或项目文件。

![](images/71.png)
![](images/68.png)

因此，最终应用插件不会改写DSH原有产品代码，也不会把DSH自身变成知识库产品；插件安装完成更不能等同于产品开发完成。最终产品和对象身份已经明确，接下来的问题是：资料、知识页、关系、问答与评估这些能力，究竟按照怎样的依赖顺序逐步生长出来？

## 2. 从运行基线到图谱数据

这条增量路线从统一运行基线开始，并以每个阶段留下的可验证项目状态为坐标。

这里先建立一个贯穿后续开发的判断框架：一个阶段只有同时出现了明确输入、实际能力调用、代码或配置变化、最窄验证以及用户可见结果，才算形成了可继续前进的项目状态。阶段名称、提交记录、截图数量和Agent的完成说明，都不能单独替代这个闭环。

![](images/72.png)

### 2.1 STAGE-00～10的因果坐标

真实Prompt总路线把完整历史分为11个主阶段。它们不是并列功能清单，而是一条逐层增加约束的开发链：

| 阶段 | 上一状态缺少什么 | 本阶段形成的直接结果 |
| :--- | :--- | :--- |
| STAGE-00 | 工作区、模型、权限与视觉能力尚未统一 | 首条开发 Prompt 之前的共同运行基线 |
| STAGE-01 | 空目录里没有可运行产品 | monorepo、共享合同、Web/API 骨架和满载工作台 |
| STAGE-02 | 每轮都要重新强调工程纪律 | 可重复选择的 `LLM Wiki 全栈工程师` Preset |
| STAGE-03 | 首页有统计数据，但资料不可操作 | 资料搜索、筛选、分页、导入、失败、重试和详情闭环 |
| STAGE-04 | 原始资料仍按各自作者的叙事存在 | 可重建、可引用、可互链的编译式 Wiki |
| STAGE-05 | Wiki 页面还不是稳定图数据 | 可重复生成的节点、边与检查器合同 |
| STAGE-06 | 节点边已经存在，但最小交互链未验证 | 消费真实 API 数据的基础 SVG 图谱 |
| STAGE-07A | 团队缺少统一的系统视图 | 可编辑、可导出的架构沟通资产 |
| STAGE-07B | 基础图谱难以识别关键关系 | 同一数据合同上的正式图谱体验 |
| STAGE-08 | 用户能阅读知识，但不能提问并核查依据 | 检索、流式回答、引用联动与无证据拒答 |
| STAGE-09 | 零散试问无法形成质量判断 | 固定题库、指标、基线、优化与回归门 |
| STAGE-10 | Agent 自报完成不能作为交付依据 | 浏览器全链路、工程验证、截图和接手文档 |

![STAGE-00～10：能力怎样逐层长出来](images/73.png)

这张坐标中有三类不同产物。STAGE-01、03、04、05、06、07B、08、09持续增加产品代码和数据合同；STAGE-02装配开发会话的工作方式；STAGE-07A交付工程沟通资产；STAGE-10负责验收和交接。把它们分开，才能看清“能力装配”与“产品开发”并没有互相替代。

### 2.2 STAGE-00：先固定运行基线

第一轮代码尚未产生之前，DSH已经需要确定四个对象：Workspace指向哪个目录、使用哪个PRO模型、当前允许怎样访问文件，以及视觉增强是否可用。DSH环境配置记录的真实环境是 `LLMWikiReproduction` Workspace、`DeepSeek-V4-Pro`、工作区写入模式和已验证的视觉增强。

![](images/74.png)

这张图需要同时观察输入框上下两处：上方Workspace是LLMwikiReproduction，下方可见工作区写入、视觉增强和DeepSeek-V4-Pro。它只证明后续任务从统一会话状态开始，并不证明任何产品代码已经生成。视觉增强也只用于检查白屏、层级、文字可读性等画面问题；按钮是否可用、数据是否真实，仍要由点击、API、console和测试共同判断。

这一步的恢复原则也很明确：路径不对就先切回正确Workspace；模型、访问模式或视觉能力不可见，就不要发送阶段Prompt。否则后面即使生成了文件，也很难判断它们写到了哪里、使用了什么能力。

### 2.3 STAGE-01：空目录开始产生可运行代码

STAGE-01是最容易被误读的地方。它不是“先规划工程”，而是从空目录直接创建一个可以启动的全栈项目。工程底座Prompt明确要求建立`pnpm workspace`，至少包含 `apps/web`、`apps/api` 和 `packages/contracts`；Web 使用 Next.js、React与 TypeScript，API使用Fastify，并提供 `/health` 和 `/api/overview`。Wiki、图谱和问答此时可以保持占位，但首页必须能够真实读取统一业务数据。

`packages/contracts` 是这一轮尤其重要的增量。统计卡、最近文档和处理进度不能由前端随意拼一套字段、后端再返回另一套字段；共享合同先固定双方都要遵守的数据形状，Web优先读取API，API不可用时才使用同结构的预置数据并明确标识状态。这样，首页即使在第一阶段使用的是预置业务数据，也已经具备可替换后端实现的工程边界，而不是一张与API无关的静态效果页。

![](images/75.png)

Prompt 的停止条件同样属于输入的一部分：只完成工程底座，实际运行 `typecheck` 与 `build`，不要提前实现文件解析、RAG、图谱算法或模型调用。对应的关键验证命令是：

```bash
pnpm typecheck
pnpm build
pnpm test
pnpm dev
```

四条命令分别回答类型合同是否闭合、生产构建是否成立、API行为是否符合预期，以及 Web/API 能否一起启动。真实过程中还修复了pnpm 11阻止 `esbuild` 安装脚本、共享contracts 缺少TypeScript依赖两类问题。修复以后，类型检查、构建、3项API测试、编译API启动和根目录开发启动链均通过。

![](images/76.png)

完成画面中可以看到启动命令、产物文件和“当前阶段还没有做什么”。这个边界很重要：此时已有真实Web／API工程和满载Dashboard，但文档正文解析、SQLite真实迁移、RAG、图谱与模型调用仍未实现。代码增量集中在 `apps/web`、`apps/api`、`packages/contracts`，可由阶段变更索引定位。

STAGE-01检查点保存的是这一里程碑的源码快照。它的作用是回看差异、定位恢复起点，而不是要求学员在本章解压运行。检查点存在只能说明这份阶段状态可恢复，不能替代当时的测试和页面结果。

### 2.4 STAGE-02：装配工作方式，不改产品源码

工程底座成立以后，新的问题不是“再写一个功能”，而是每轮都要重复声明范围、Skill读取、测试、视觉验收和停止条件。STAGE-02因此切换到DSH的创造模式，把标准模式复制并定制为LLM Wiki全栈工程师。Preset创建Prompt点名目录ID、显示名称和七条开发约束，并明确要求不要修改产品源码。

![](images/77.png)

标准模式提供文件、Shell、Skills、计划和工作流等通用编码底座；创造模式负责读取、复制和定制Preset。最终产物不是一段聊天提示词，而是用户Preset目录中的真实配置：`preset.yml` 保存名称、说明与排序，`agent.cordis.yml` 保留标准编码工具，并加入中文 persona、Skill发现和分阶段验证纪律；随附的 `find-plugins` Skill 继续提供插件发现能力。

真实创建过程没有一次成功。临时注册的探针工具没有进入当前轮次已经冻结的工具表，随后出现重复空调用。恢复Prompt没有要求“继续尝试”，而是根据已观察事实收窄路径：停止探针、读取标准模式与发现规则、复制标准Preset，再只修改显示元数据和persona。因为用户级Preset目录位于Workspace之外，写入还必须经过一次明确审批。

![](images/78.png)

审批画面证明的是作用域边界：产品代码仍留在Workspace，Preset写入DSH用户级目录。之后再做 YAML解析、Preset 发现和 `broken` 状态检查。

![](images/79.png)
![](images/80.png)

两个画面分别回答“配置能否被DSH发现”和“新会话能否真正选择”。STAGE-02的成果到此为止：开发纪律变成了可重复装配的会话能力。Preset不会替用户选择Workspace、模型、访问权限或视觉增强，更不会自动生成产品代码。
